# 회신 — 검토 보고 판정 및 결정 (2026-11-10, 기획 측)

검토 보고(R-1~R-6) 전건 접수했다. 보고 수준이 기준을 충족한다 — 특히 문서 간 불일치를 코드 근거로 잡아낸 부분. 아래 결정은 전부 확정이다. 문서 정정은 기획 측이 이미 반영했으니, 정정본 패키지를 기준으로 삼아라.

## 1. 보고에서 확정된 사실 (기획 측 실측과 합쳐진 정본)
- 라이브는 예전 빌드다. "100%" 문구는 작업 트리 소스에서 이미 0건 — 남은 일은 문구 수정이 아니라 **배포**다 (WI-01 범위로 흡수).
- 약관 4종 오류와 파트너 로그인 실패는 **단일 원인(API 530)** 이다. 별개 결함으로 세지 않는다.
- 푸터 사업자 정보는 코드에 있고 값이 비어 있다. 값 입력은 Phase 0에서 CEO 제공 값으로 채운다 (아래 4번).
- 정산 코드는 재생 × 단가(기본 10원) + 위반 시 전액 몰수 구조임을 확인했다.

## 3. 충돌 13건 처리 (R-2)
- 전건 수용한다. 문서 쪽 잘못(1·4·6번)은 기획 측이 정정 완료. 코드 쪽(7·8·9·10·13번)은 해당 WI의 완료 조건으로 편입했다 (작업지시 정정본 참조).
- 11번(WI 번호): **작업지시서의 번호가 정본**이다. 다른 세션 주석의 WI 표기는 각 항목 착수 시 같은 커밋에서 정정한다.
- 12번(canonical): **엔진 범위에서 제외 확정.** 화면 담당 지정 전까지 보류하고, 엔진은 WI-03에서 메일·설정 도메인만 다룬다.

## 4. 집행 구조 (확정)
- 1차 지시: WI-01·02·03·04·06 (재산정 약 41~46개, 상한 50) — 기준선 커밋 후 PO 승인으로 착수.
- 후속 지시: WI-05·07·08 — 판매 채널 상품이 생긴 뒤 정산 원천이 생기므로 순서상 손해 없음 (네 분리 제안 수용).
- CEO 제공이 필요한 유일한 입력: **사업자 정보 실제 값** (푸터·약관 기입용). Phase 0 배포 전까지 받으면 되므로 지금 집행을 막지 않는다.
- R-4 추출표는 전건 수용한다. 제16조 공지 기능만 NOT CONFIRMED로 남아 있는데, 이건 WI-06 착수 시 확인 항목으로 넣어라.

## 6. 추가 지시 — 사업자 표시 (2026-11-10, CEO 지시)
사업자 등록·신고가 아직 안 된 상태다. 따라서:
- 사업자 표시가 들어가는 모든 자리(푸터 블록, 약관의 사업자 표시사항, 결제·정산 화면의 사업자 정보)의 **코드는 완성**하되, **화면에는 숨김(hide) 처리**한다.
- 숨김은 값(VITE_BUSINESS_* 등)이 비어 있을 때 블록 자체가 렌더링되지 않는 기존 구조를 유지·확정하는 방식으로 한다 — 라벨만 남거나 빈 칸이 보이는 상태는 불합격이다.
- 전환은 값 입력만으로 가능해야 한다 (신고 완료 → 값 입력 → 표시 on). 코드 재수정 없이 설정만으로 켜지게 한다.
- 표시를 숨긴 것과 별개로, **유료 판매 개시는 사업자 등록·신고 완료가 게이트**다. 숨김 처리가 판매 개시를 허용한다는 뜻으로 해석하지 마라.

## 7. 추가 요청 — QA 전용 계정 발급 (2026-11-10, CEO 지시)
기획·검증 세션(Claude)이 라이브를 직접 눌러보려면 전용 계정이 필요하다. 아래 기준으로 발급해 달라.
- 종류: **일반(리스너) 계정 1개 + 파트너 계정 1개.** 가능하면 관리자 열람 계정 1개도.
- 조건: 실사용자·실정산 데이터와 섞이지 않게 테스트 표식을 붙인다. 결제수단은 연결하지 않는다 (결제 검증은 테스트 키로 별도).
- 용도: 여정 단위 라이브 실측 전용 (가입·로그인·업로드·정산 화면 확인). 이 계정으로 실제 유통·정산이 발생하게 만들지 않는다.
- 전달: 비밀번호를 채팅·문서에 평문으로 적지 마라. 발급 사실과 아이디만 보고하고, 비밀번호는 보안 입력 경로(Secure Vault)로 전달한다.
- 발급 시점: WI-01(서버 정상화)로 로그인이 살아난 직후. 지금 있는 파트너 테스트 계정은 서버 오류로 로그인이 막혀 있어 대체가 안 된다.
